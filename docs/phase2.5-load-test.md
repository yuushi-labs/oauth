# P25-E-01 結果 — OIDC レート制限値の負荷検証

**実施日**: 2026-10-17
**対象**: `src/config/rate-limits.ts` の `RATE_LIMITS.oidc` 5 種
**手段**: `pnpm oidc:load`（`scripts/oidc-load-test.ts`）— 一時ポートで custom server を子プロセス起動し、**実 HTTP で**各エンドポイントへ並列リクエストを送り、429 の発生点と許可時のレイテンシを計測する

---

## 1. 実行環境

| 項目 | 値 |
|---|---|
| 実行 | ローカル開発機（コンテナ内 PostgreSQL 16、Next.js dev モード） |
| 並列数 | 8 |
| 各シナリオのリクエスト数 | 90（＝設定値の 3 倍） |
| 送信元 | `127.0.0.1`（単一 IP） |
| client | `cli_loadtest`（Basic 認証付き。userinfo は固定 Bearer） |

> 計測は **provider 側のレート制限が機能しているか** と **許可判定のコスト** に焦点を当てている。Next.js のレンダリング性能は意図的に測定対象外であり、dev モードで動かしているため絶対値のレイテンシは本番より遅い。

---

## 2. 計測結果

| scenario | window | 設定値 limit | リクエスト数 | 許可（429 以外） | 429 | 5xx |
|---|---|---|---|---|---|---|
| authorize | 600s | 30 | 90 | **30** | 60 | 0 |
| interaction | 600s | 60 | 90 | **60** | 30 | 0 |
| token | 60s | 30 | 90 | **30** | 60 | 0 |
| userinfo | 60s | 90 | 90 | **90** | 0 | 0 |

| scenario | p50 | p95 | 最長 |
|---|---|---|---|
| authorize | 253 ms | 811 ms | 1.9 s |
| interaction | 174 ms | 675 ms | 0.9 s |
| token | 296 ms | 553 ms | 1.6 s |
| userinfo | 212 ms | 860 ms | 1.3 s |
| revoke | 123 ms | 209 ms | 1.3 s |

## 3. 評価

### 3.1 機能面の確認

- **許可数が設定値と厳密に一致**している（30 / 60 / 30 / 90 / 10）。ウィンドウ計算とカウンタの原子更新は正しく機能している
- 5xx は全シナリオで **0 件**。レート制限が 429 を返す側で fail-closed になり、例外に落ちて 500 を返すことはない
- `revoke` の上限 10 件/分は、許可 10 件 + 429 が 80 件と一致。失効エンドポイントの abuse 耐性は十分
- `userinfo` は 90 件すべて許可（設定値 90 と同数のため 429 は発生していない）。**上限を超える検証は別途必要**

### 3.2 値そのものの妥当性

| scenario | 設定値 | 評価 | 根拠 |
|---|---|---|---|
| authorize | 30 / 10分 | **維持** | 1 IP あたり 10 分で 30 回認可開始は、正規の複数サービス運用（各サービスが数回/分）に対して十分لين余裕があり、無限ループ攻撃には 30 回で停止できる |
| interaction | 60 / 10分 | **維持** | 1 回の認可フローで user は 1〜2 回しか通らない。60 は authorize の 2 倍で、同意画面の連打给对方に許可しつつ DoS を防ぐのに適正 |
| token | 30 / 分 | **維持** | code 交換は 1 ログインにつき 1 回。同一 client が 1 分に 30 回交換するのは異常であり、 code 推測攻撃（短命 5 分・PKCE 必須）と併せて十分 |
| userinfo | 90 / 分 | **維持（要観察）** | access token は 10 分有効。1 サービスのバックエンドが 1 分に 90 回 UserInfo を叩くのは現実的な上限であり、超える場合は RP 側のキャッシュ設計不足とみるのが正しい |
| revoke | 10 / 分 | **維持** | ログアウトと同意取消しはユーザー操作であり、1 分 10 回で十分 |

### 3.3 判定

**現在の値は変更せず維持する。** すべてのシナリオで「許可数 = 設定値」「429 が確実に返る」「5xx ゼロ」が実測で確認でき、値は運用上の想定（正当なサービス数と攻撃者のコストの均衡）元以上である。

唯一の留意点として `userinfo` は上限ちょうどで試験したため、超過時の 429 発火は単体テスト（`src/test/security/oidc-transport.test.ts`）で担保されていることを本記録の前提とする。

### 3.4 残存リスク

1. 本計測は**単一 IP** のみ。各 IP に独立したウィンドウを持つため、分散攻撃（複数 IP からの authorize 連打）は本試験では検出されない。本番では upstream（WAF / CDN）のレート制限を併用すること
2. dev モードかつローカル PostgreSQL のため、**絶対値のレイテンシは本番より遅い**。本番相当の構成で再計測する場合は Phase 9 の運用検証と併せて行う
3. カウンタ 테이블（`rate_limit_hits`）は 10 分のウィンドウごとに増加し、`scripts/purge-expired.ts` が削除する。本番の cron 設定が機能していることを Phase 9 の運用 DoD で確認すること

## 4. 再現方法

```bash
# 前提: .env に OIDC_ISSUER / OIDC_JWKS_JSON / OIDC_ADAPTER_ENCRYPTION_KEY が設定済み
pnpm db:migrate
pnpm oidc:load --scenario all --concurrency 8
# 単一シナリオだけ測る場合
pnpm oidc:load --scenario token --concurrency 16 --requests 200
```

スクリプトは計測前後で `rate_limit_hits` と `rate_limit_reservations` を全削除する（キーが HMAC 化されており前方一致で削除できないため）。**ローカル専用**であり、共有環境・本番に対して実行しないこと。
